# 设计与逆向说明

本文记录「流畅指挥」补丁的原理、逆向依据、以及**实测得出的边界**。
所有地址以 `Game.dll` 的 **RVA**（VA − 0x6F000000）给出，代码里按实际模块基址换算。

---

## 1. 问题现象

魔兽争霸 III 在大编队（数百单位）移动时，指令响应明显变慢：
点下移动后要等一会儿单位才动，队伍越大越明显。

---

## 2. 引擎结构：移动微步的槽位 FIFO

逆向结论：引擎把「移动微步」（path micro-step）放进按槽位组织的 FIFO 队列。

关键函数（1.24e）：

| RVA | 作用 |
|---|---|
| `0x0049BE06` | 槽号计算处 1：`mov eax, edx` + `shr eax, 0x10` |
| `0x0049C0B9` | 槽号计算处 2：`mov eax, ecx` + `shr eax, 0x10` |
| `0x00A9B018` | 槽表基址（16 槽，步长 0x70，子块 +0x54，标志 0x2000000） |
| `0x0049C3A0` | 放行判定：决定本 tick 该节点能否通过 |

**原始槽号 = `(flags >> 16) & 0xF`** —— `flags` 是玩家/路径分组号，
因此**同一玩家的所有单位挤在同一个槽**，而每个 tick 只放行队头 1 个。

这就是大编队变慢的直接原因：N 个单位排队，每 tick 只走 1 个。

---

## 3. 补丁做法

把槽号计算的输入从 `flags` 换成 `path`：

```asm
; 原始
mov eax, edx          ; eax = flags
shr eax, 0x10         ; (flags >> 16)
and eax, 0xF          ; & 0xF  → 1 个槽

; 补丁后
mov eax, ecx          ; eax = path
shr eax, 0x0C         ; (path >> 12)
and eax, 0xF          ; & 0xF  → 16 个槽散列
```

不同 path 散列到 16 个槽，**16 条队列并行推进**，同槽排队长度降到 1/16。
槽表结构本身不需要改。

### 版本适配

`SlotPatch.cpp` 里用 `Profile` 表按版本存放补丁点：

| 版本 | 补丁点数 | 槽表 RVA |
|---|---|---|
| 1.24b | 4 | 0x00A9B018 |
| 1.24e | 4 | 0x00A9B018 |
| 1.25b | 4 | 0x00A84FF8 |
| 1.26 | 4 | 0x00A84FF8 |
| 1.27a | 8 | 0x00BC5FF8 |

**识别方式是签名匹配，不是版本字符串**：逐字节比对每个补丁点的原值，
全部匹配才认为是该版本。这样官方安装版 / 绿色版 / 不同语言版都能正确识别。

### 安全设计

- 补丁前校验 `SizeOfImage`，所有读写都在模块映像范围内，不越界；
- 每个补丁点先比对原字节，不匹配就整体跳过，**绝不盲写**；
- 重复注入会被识别（比对已打补丁的形态），不会重复写；
- `SLOT_DRY=1` 只校验 + 写日志，不动内存，用于排查。

## 4. 代理 DLL（ijl15_proxy）

目的：让玩家**直接双击 War3.exe** 也能生效，不必每次都用启动脚本。

做法：

1. 安装时把原版 `ijl15.dll` 改名成 `ijl15_orig.dll`；
2. 代理 DLL 放到 `ijl15.dll` 的位置，导出表把全部 6 个函数
   （`ijlInit` / `ijlFree` / `ijlRead` / `ijlWrite` / `ijlErrorStr` / `ijlGetLibVersion`）
   转发给 `ijl15_orig`；
3. `DllMain` 起一个线程 `LoadLibrary(<游戏目录>\patch\SlotPatch.dll)`。

选 `ijl15` 的原因：它只有 6 个导出，转发面最小，且游戏启动早期就会加载。

**导出转发用 `#pragma comment(linker, "/export:...")`，不要同时提供 .def** ——
两者叠加会触发 `LNK4197` 重复导出警告和 `LNK2001` 无法解析符号。

## 5. 实测得出的边界（重要）

以下结论都来自进程内采样 + 计时钩子实测，不是推测。

### 5.1 寻路并行不是瓶颈

| 指标 | 实测值 |
|---|---|
| pathing tick 耗时 | 385 ~ 1293 μs，平均 **882 μs** |
| tick 频率 | 约 **30 次/秒** |
| 合计 CPU 占比 | 约 **3%** |

即使把寻路完全并行化，理论上限也只有 3%。补丁的真实收益来自
**减少同槽排队**（降低延迟），而不是提升吞吐。

### 5.2 真正的 CPU 大头是 memcpy 和内核/GDI

在 1850 单位场景下采样（400 Hz × 20 s）：

| 模块 | 占比 |
|---|---|
| Game.dll | 23 ~ 67%（随场景波动）|
| MSVCR80.dll | 0.8 ~ 21%（几乎全是 memcpy）|
| ntdll.dll | 13 ~ 34%（系统调用）|
| nvd3dum.dll | 5 ~ 22%（显卡驱动）|
| win32u.dll | 3 ~ 15%（GDI/窗口）|

`memcpy` 峰值曾达 18~22%，调用者集中在 `Game.dll +0x52E4DF`（逐行 32 位像素 blit）、
`+0x5314F2`（2 字节元素追加）、`Storm.dll +0x25ECB`。
一次 75 秒对局约 **700 万次 memcpy 调用，平均每次 322 字节** —— 属调用开销受限。

**替换 memcpy 实现没有收益**（实测持平甚至更慢）：
MSVCR80 的 SSE2 版本已经足够好，瓶颈是调用次数而非单次效率。

### 5.3 秒级卡顿来自路径请求突发

卡顿帧的 cluster 数会从正常的 200~400 暴涨到 **3000~9000**，
而该帧 cluster 更新循环本身只花 5~8 ms，游戏却停 1~5 秒 ——
时间花在**产生这些 cluster 的路径计算**上。

这解释了「平均寻路只占 3%，但会卡」的矛盾：**寻路是突发的**。

> 注意：早期用「每 5 ms 挂起/恢复主线程」的采样器测得的秒级卡顿，
> 有相当一部分是**采样器自身干扰**造成的。关掉采样器后，
> 稳态最坏帧间隔只有 63 ms（约每 25 帧一次的引擎周期性工作）。

### 5.4 全屏 vs 窗口

同条件 A/B（都在真实战斗中）：

| 指标 | 窗口模式 | 全屏模式 |
|---|---|---|
| 平均帧间隔 | 24~29 ms | 28~29 ms |
| 最坏卡顿 | 4297 ms | 2984 ms |

全屏把最坏卡顿改善约 30%，但**平均帧率不变**，秒级卡顿依然存在
（因为它由路径突发驱动，与渲染方式无关）。

### 5.5 尝试过但放弃的方向

| 方向 | 结果 |
|---|---|
| 多 worker 线程并行 cluster 更新 | **不可行**：引擎 cluster 代码会写全局暂存区，2 个以上 worker 必然崩/死锁。唯一安全的是 1 worker + offload（把处理挪出主线程）|
| 每线程暂存栈（TLS + code cave） | 能消除崩溃，但 2 worker 仍挂起；且需大量 cave 代码 |
| 替换 memcpy 实现 | 无收益（见 5.2）|
| `PATH_K` 限流（每槽每 tick 放行 K 个） | 实测最坏卡顿 4922→1594 ms，但**原实现会乱序出队破坏 FIFO**，导致点「选项」崩溃，已撤除 |

## 6. 构建

`build.bat` 用 MSVC x86 编译三个目标，`/O2 /W3 /EHsc /utf-8`。

`SlotPatch.cpp` 与 `ijl15_proxy.cpp` 都是纯 Win32 API + CRT，无第三方依赖。
源码按 GCC / MSVC 双兼容写法（避免 `__try`，改用 PE 边界校验 + 签名校验）。
